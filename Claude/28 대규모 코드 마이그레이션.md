# 대규모 코드 마이그레이션

프로덕션 코드베이스를 다른 언어·프레임워크로 옮기는 **코드 마이그레이션**은 최근까지 다년(multi-year) 프로젝트였다. Anthropic 블로그 "How Anthropic runs large-scale code migrations with Claude Code"(2026-07-16)는 지난 한 달간 Anthropic 내부 개발자들이 Claude Fable 5, Claude Opus 4.8, 그리고 [[08 서브에이전트와 에이전트 팀|다이내믹 워크플로우]]를 이용해 수만~수십만 줄 규모 패키지 10개를 마이그레이션한 경험에서 뽑아낸 6단계 프로세스와 베스트 프랙티스를 정리한다.

핵심 통찰 한 문장: **"You don't fix the code. You fix the process (loop) that produced the code."** — 생성된 코드를 손으로 고치지 말고, 그 코드를 만들어낸 규칙과 루프를 고쳐서 다시 돌린다.

## AI 코드 마이그레이션이란

AI 코드 마이그레이션은 에이전트가 프로덕션 코드베이스를 새 언어·프레임워크로 옮기는 작업이다. 파일을 손으로 번역하는 대신 엔지니어가 마이그레이션 규칙과 검증 루프를 작성하고, 에이전트가 번역·컴파일·테스트를 반복해 새 코드의 동작이 원본과 일치할 때까지 수렴시킨다. 이 방식이 다년짜리 프로젝트를 몇 주로 압축한다.

## 왜, 언제 마이그레이션하는가

마이그레이션은 최초 구축 시점과 현재 사이 환경이 달라졌을 때 시작된다 — 알려진 트레이드오프가 한계에 도달했거나, 더 나은 접근이 등장했거나, 기존 생태계가 축소되고 있는 경우다. 예컨대 Bun 공동창업자 Jarred Sumner는 "LLM 이전 시절 오클랜드의 좁은 아파트에서 1년 만에 Bun을 쓰기 위해" C급 성능과 급진적 단순성을 주는 Zig를 택했지만, 이제 Bun CLI가 월 1000만 다운로드를 넘기면서 그 트레이드오프가 부담이 됐다.

**비용-편익은 여전히 실재한다.** 백만 줄급 마이그레이션이 더 이상 4년짜리 프로젝트에 $3~4M 엔지니어링 리소스를 태우지는 않지만, 여전히 실행에 수만~수십만 달러 이상이 든다 — Bun 마이그레이션은 uncached input token 59억 개 + output token 6.9억 개를 소비해 API 가격 기준 약 $165,000이 들었고, Mike Krieger의 포트 주요 구간은 토큰 2,700만 개를 썼다. 다만 실존적 명분까지는 필요 없어졌다 — changelog에 쌓인 1년치 메모리 버그 패치나 만성적 병목 하나로도 이제는 정당화된다. 최악의 시나리오도 "브랜치를 지우고 다시 시도"로 끝난다는 점이 커리어 리스크를 낮췄다.

## AI가 마이그레이션 수학을 바꾸는 이유

Claude Fable 5는 Anthropic의 가장 강력한 GA 모델이며, Fable과 Opus 4.8은 서브에이전트로 병렬 워크스트림을 위임·지휘·검증하는 데 특히 뛰어나다. 대규모 마이그레이션이 이 모델들에 잘 맞는 이유:

- **병렬적이다** — 파일·크레이트 같은 독립 단위 수천 개에 걸쳐 동시에 작업할 수 있다.
- **컨텍스트가 명확하고 포괄적이다** — 기존 코드 자체가 훌륭한 스펙이자 번역 규칙집의 근거가 된다.
- **내장 판정자(referee)가 있다** — 테스트 스위트가 있으면 사람의 개입 없이도 며칠씩 ground truth에 대고 갈 수 있다.
- **큐가 스스로 채워진다** — 컴파일러나 테스트가 실패하면 그게 곧 다음 작업 항목이다.
- **일관성·엣지케이스 처리가 구조화된다** — 리뷰어가 위반 사항마다 근거 규칙을 인용하므로 드리프트가 조용히 묻히지 않고 큐 항목이 되며, 에이전트가 엣지케이스를 만나면 그 수정이 이후 모든 에이전트가 따르는 규칙이 된다.

## 사전 준비 — 판정자(judge)부터 세워라

마이그레이션을 시작하기 전 반드시 **원본 코드와 타깃 코드를 동등한 기준으로 평가할 강력한 판정자**를 마련해야 한다. 그래야 종료 조건과 성공 기준이 생긴다. 원본 언어로 쓰인 테스트 스위트는 보통 타깃 코드에 없는 내부 함수에 의존하므로 그대로 못 쓴다. 판정자를 만드는 절차:

1. **기존 테스트 분류** — Claude로 어떤 테스트가 외부 호출로 표현 가능한지, 어떤 것이 포팅되지 않을 내부 구현에 의존하는지 가려낸다.
2. **이식 가능하게 재작성** — 외부에 노출된 테스트를 원본·포트 양쪽에서 돌아가는 assertion으로 변환한다. 적대적(adversarial) 에이전트로 재작성된 테스트가 검증 강도를 약화시키지 않았는지 확인한다.
3. **판정자 검증** — 원본 코드에 돌려 통과하는지, 일부러 망가뜨린 코드에 돌려 실패하는지 확인한다. 깨짐을 못 잡는 판정자는 판정자가 아니다.

Jarred는 이미 TypeScript로 작성된 대형 테스트 스위트가 있었지만, 대부분의 프로젝트는 그렇지 않다. Mike는 Python→TypeScript 포트에서 실제 시나리오 7개짜리 parity harness를 직접 만들고 동작이 하나라도 달라지면 버그로 취급했다.

## 6단계 워크플로우

구조 보존형 마이그레이션(Jarred, Zig→Rust)과 재설계형 마이그레이션(Mike, Python→TypeScript)은 세부 실행이 다르지만 같은 6단계로 일반화된다.

### 1단계 — 규칙집, 의존성 맵, 갭 인벤토리 작성
- **규칙집(rulebook)** 순서가 갭 인벤토리보다 먼저다 — 갭 인벤토리는 규칙집의 기본값이 커버하지 못하는 부분으로 정의되고, 둘은 합동 감사(joint audit)로 함께 검증된다. 새 코드가 기존 구조를 그대로 따를지(구조 보존, Jarred) 완전히 재설계될지(Mike)에 따라 규칙집의 성격이 갈린다 — 전자는 타입·관용구 변환 lookup table, 후자는 설계 문서에 가깝다. Jarred는 Claude와 대화하며 애매한 영역마다 정책을 세우고, 자신의 직관에 기반한 8가지 흔한 실패 유형을 리뷰하는 서브에이전트 8개를 따로 운용했다.
- **의존성 맵**은 파일 간 종속 관계를 파악해 병렬 마이그레이션 작업을 어떤 순서·배치로 나눌지 정한다. Claude Code로 결정론적 스크립트를 만들고 돌려 이 맵을 생성한다.
- **갭 인벤토리**는 언어 간 근본적 차이(예: Zig→Rust의 수동 메모리 관리 vs 소유권, Python→TypeScript의 암묵적 vs 명시적 인터페이스 계약)를 미리 목록화한다. Jarred는 사전에 갭을 인벤토리화했고, Mike는 먼저 번역한 뒤 사후 감사로 갭 인벤토리를 만들었다 — 프로젝트에 따라 둘 다 필요할 수 있다.

### 2단계 — 규칙 스트레스 테스트
전체 마이그레이션 전에 치르는 "shakedown cruise"다. Jarred는 에이전트 하나로 규칙집을 따라 파일 3개를 번역하고, 다른 에이전트 하나로 "시니어 Rust 엔지니어처럼" 파일 3개를 번역한 뒤, 세 번째 에이전트로 두 결과의 diff를 이용해 새 번역 규칙을 만들게 했다. 이 단계에서 전체 1,448개 파일에 fan-out했다면 문제를 일으켰을 치명적 이슈 2개를 잡아냈다. 이 스트레스 테스트는 두 번역본을 줄 단위로 비교 가능한 **구조 보존형 마이그레이션에만** 통한다 — 재설계형(Mike)이라면 설계 문서 자체를 적대적 리뷰어로 공격하고 disposable end-to-end 실행으로 검증하는 것이 등가물이다. 어느 쪽이든 번역된 파일은 버린다 — 목표는 진도가 아니라 규칙 정제다.

### 3단계 — 전체 번역
나머지 단계는 모두 같은 다중 에이전트 루프(구현 → 리뷰 → 수정)를 돈다. 구현자(implementer) 작업은 더 작은 모델에, 리뷰어는 더 큰 모델에 맡길 수 있다 — Mike는 메인 마이그레이션에서 서브에이전트 12개를 fan-out할 때 Claude Sonnet을 썼다. 작업 큐는 기계적이어야 한다 — 배치 스크립트가 디스크에 번역 파일이 존재하는지만으로 완료 여부를 판단하고 대기 중인 파일을 배치로 슬라이스한다. 큐가 매번 디스크에서 재구성되므로 마이그레이션은 설계상 재개 가능(resumable)하다. 구현자가 확신 없이 처리하지 못한 부분은 `// TODO(port): <reason>`으로 플래그해 4단계로 넘긴다. 적대적 리뷰어 2개가 서로 다른 컨텍스트로 구현자의 작업을 평가하고, 둘의 의견이 갈리면 세 번째 에이전트가 판정한다. 같은 실수가 여러 파일에서 반복되면 파일별 수정이 아니라 규칙집에 한 문장을 추가하고 영향받은 배치를 재생성한다 — 규칙집은 이 단계 내내 계속 자라고, 코드는 그에 맞춰 손으로 패치되지 않는다. 컴파일러를 루프 안에 둘지(Mike, TypeScript 컴파일러는 몇 초면 끝남)는 언어별 컴파일 비용(Jarred, cargo는 분 단위라 컴파일러를 4단계로 미룸)에 달렸다.

### 4~6단계 — 컴파일, 실행, 동작 일치 확인
세 단계는 같은 루프 아키텍처를 공유하며 갈수록 사람의 판단이 덜 필요해진다. 4단계는 언어·규모에 따라 3단계에 흡수되기도 한다.
- **4단계(컴파일)**: Jarred는 워크스페이스 전체에 컴파일러를 한 번 돌리는 오케스트레이터 스크립트를 쓰고, "fixer agent"들이 에러 목록을 병렬로 적대적 리뷰와 함께 처리한 뒤 빌드를 재실행하는 식으로 반복했다. 순환 import를 고치자 Zig의 지연 컴파일이 눈감아주던 Rust 모듈 에러 수천 개가 쏟아졌는데, 어떤 의존관계를 지우거나 옮기거나 경계를 재구성할지 분류하는 로직을 루프에 넣어 해결했다.
- **5단계(실행·스모크 테스트)**: 스모크 테스트에서 나온 크래시가 컴파일러 에러 목록과 같은 역할의 기계적 소스가 된다. 근본 원인별로 그룹화해 적대적 서브에이전트가 리뷰한다.
- **6단계(동작 비교)**: 사전 준비 단계의 테스트 스위트를 샤딩해 돌리고, 실패는 두 코드베이스를 모두 대조하는 "fixer agent"로 처리한 뒤 적대적 리뷰어가 수정을 검증한다. 이 단계에는 **build daemon**이 등장한다 — 바이너리를 재빌드할 수 있는 유일한 프로세스로, fixer들이 패치를 쓰면 daemon이 배치로 모아 한 번에 재빌드하고 영향받은 테스트만 재실행해 결과를 되먹인다. 이는 여러 에이전트가 각자 재빌드를 트리거하는 대신 가장 비싼 연산을 직렬화한다. 같은 실패가 반복되면 그 버그를 만든 규칙을 고치고 그 규칙이 건드린 파일만 재생성한다. Mike처럼 포팅된 테스트 스위트가 없다면, Claude로 실제 시나리오 몇 개를 양쪽 코드베이스에 돌려 diff하는 작은 스크립트를 만들게 하면 된다 — 그는 7개 시나리오로 시작해 전부 통과할 때까지 fix agent를 돌렸고, 이후 Claude가 스스로 설계한 end-to-end 테스트 스위트를 나흘 밤 연속 자율 실행시켜 시나리오 목록으로는 못 잡았을 자잘한 문제까지 걸러냈다. 판정 스위트가 없다는 것이 이 단계를 막는 이유가 되지 않는다 — 판정자를 물려받을 수 없다면 Claude에게 만들게 하라.

## 베스트 프랙티스

- **이 가이드를 맹목적으로 따르지 말 것** — 각 마이그레이션은 다르다. 시작점으로 삼고 Claude와 함께 자신의 마이그레이션을 구체적으로 계획하라.
- **개별 실패에 집중하지 말 것** — 개별 실패는 루프의 몫이다(fixer agent가 태운다). 주의는 패턴에 두라.
- **리뷰는 적대적으로, 검증은 기계적으로** — 적대적 리뷰는 더 긴 실행 시간을 정당화할 만큼 값어치가 있다. 컴파일러·diff·테스트 스위트 같은 스크립트가 판정자가 되게 하라.
- **가장 큰 모델을 모든 곳에 쓰지 말 것** — 토큰 소비는 루프에 집중되니 의도적으로 설계하라. 작은 모델은 고볼륨 구현 fan-out에 적합하고, 가장 큰 모델은 리뷰어와 다른 에이전트가 따를 규칙을 쓰는 역할에 아껴 두라.
- **사람의 시간을 앞으로 당길 것** — 규칙집과 스트레스 테스트가 가장 시간이 많이 든다. 그 이후는 대체로 큐가 소진되는 과정이다.
- **작업 큐는 기계적이고 재개 가능하게** — "완료"는 "출력 파일이 디스크에 존재한다"를 의미해야 한다.

## 사례: Bun (Zig → Rust)

Bun 공동창업자 Jarred Sumner가 Bun을 Zig에서 Rust로 마이그레이션했다. 약 백만 줄의 코드가 2주 미만에 생성됐고, 병합 전 Bun의 기존 테스트 스위트 100%가 CI에서 통과했다. 병합 후 회귀 19건이 나왔고 모두 수정됐다. Rust 포트는 6월 Claude Code에 탑재되어 출시됐다. Rust 코드의 약 4%는 C/C++ 경계의 단일 라인 포인터 연산 위주로 `unsafe` 블록 안에 있다. 개선 수치: 2,000회 반복 빌드 기준 메모리 사용량이 6,745MB → 609MB로, Linux/Windows 바이너리 크기가 19% 감소, HTTP 서빙과 next build·tsc 같은 실제 워크로드에서 2~5% 빨라졌다. 이 마이그레이션은 uncached input token 59억 개 + output token 6.9억 개(API 가격 기준 약 $165,000)를 소비했다.

## 사례: Python → TypeScript

Anthropic Labs 공동 리드 Mike Krieger가 내부 도구의 Python 코드베이스를 165,000줄의 TypeScript로 주말 동안 마이그레이션했다. 계기는 컴파일 단계였다 — 단일 바이너리로 배포하는 이 도구는 Python 툴체인으로 플랫폼당 약 8분, 빌드 매트릭스 전체로는 릴리스마다 30분을 잡아먹었다. 포팅 후 같은 컴파일이 약 2초로 줄고 바이너리 시작 속도가 6배 빨라졌으며, 별도 배포 파이프라인을 폐기할 수 있었다. 이 과정에는 에이전트 수백 개, 8단계 관문(phase gate), 적대적 리뷰 3라운드, 그리고 Python 원본과 모든 명령의 출력을 diff하는 최종 parity 체크가 들어갔다. Mike는 전체 마이그레이션을 엔드투엔드로 3번 돌려 매번 결과를 버리며 규칙과 워크플로우를 수정했고, 세 번째 실행에서 결과를 채택했다. 주요 구간은 토큰 2,700만 개를 소비했다.
