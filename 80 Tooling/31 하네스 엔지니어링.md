# 31 하네스 엔지니어링

**하네스(harness)**는 사용자의 의도와 모델의 다음 토큰 사이에 있는 모든 것이다 — 루프, 컨텍스트 예산, 도구 디스패치, 권한, 복구. 모델은 상태 없는 함수이고, 에이전트가 가진 것처럼 보이는 기억·안전성·능력은 전부 그 주변 루프에 **엔지니어링해 넣은 것**이다. `awesome-ai-harness`의 표현을 빌리면 "모델은 엔진이고 하네스는 자동차"다.

이 노트가 다루는 것은 프레임워크 목록이 아니라 그 아래 층이다. 같은 프런티어 모델이 나쁜 하네스에 들어가면 나쁜 모델처럼 행동한다 — 루프에 빠지고, 잊고, 엉뚱한 도구를 부르고, 노이즈에 컨텍스트를 태우고, 포기한다. 그 격차의 대부분은 모델 가중치에 없다.

## 하네스의 6가지 런타임 책임

큐레이션이 인용하는 학술 서베이(*From Question Answering to Task Completion: A Survey on Agent System and Harness Design*)는 모든 하네스가 답해야 하는 런타임 책임을 여섯 가지로 열거한다.

| 책임 | 질문 |
|---|---|
| session state | 세션 간 무엇이 남고 무엇이 사라지나 |
| context budgeting | 유한한 컨텍스트를 무엇에 쓰나 |
| tool dispatch | 어떤 도구를 언제 노출하고 호출하나 |
| provider abstraction | 모델·프로바이더 교체가 상위 층을 깨지 않나 |
| permissions | 무엇을 사람의 승인 없이 하나 |
| recovery | 실패했을 때 어떻게 돌아오나 |

이 여섯 개가 **하네스와 프레임워크를 가르는 선**이기도 하다. Arize의 정리에 따르면 "harness"가 "framework"를 밀어내는 이유는 소유권의 차이다 — **하네스는 루프를 소유하고, 프레임워크는 부품을 빌려줄 뿐**이다.

## 컨텍스트 엔지니어링 — 하네스 품질의 대부분이 사는 곳

컨텍스트 윈도우는 에이전트의 작업 기억 전체이며, 능동적으로 관리해야 하는 **희소 자원**이다.

- **Manus의 실무 교훈** (가장 많이 인용되는 실무 문서): KV-cache를 중심으로 설계한다(안정적인 prefix, append-only 히스토리) · 도구를 제거하지 말고 **tool logit을 마스킹**한다 · 파일시스템을 무한 컨텍스트로 쓴다 · 목표를 recency 윈도우에 **되읊는다**(recitation) · **실패를 컨텍스트에 남긴다**(모델이 그로부터 배우게).
- **Context Rot** (Chroma의 측정 연구): 입력이 커질수록 성능이 **비균일하게** 떨어진다 — 사소한 과제에서도. 위 처방들이 필요한 경험적 근거가 이것이다.
- **긴 컨텍스트의 4가지 실패 모드** (Drew Breunig): `poisoning`(오염) · `distraction`(주의 분산) · `confusion`(혼동) · `clash`(충돌). 대응 처방은 RAG · tool loadout · quarantine · pruning · summarization · offloading.
- **Lost in the Middle**: 컨텍스트 내 **위치**가 중요하다 — "길게 넣으면 된다"가 실패하는 이유.

이 vault의 L1(`hot.md` INJECT 블록) → L2(MOC) → L3(노트) 계층은 위의 `just-in-time retrieval` + `stable prefix` 조합에 해당한다. INJECT 마커 안쪽을 안정적으로 유지하는 규칙이 정확히 KV-cache 친화 설계다.

## 관측성·평가 — 2026-08 기준 생태계의 성장축 (직접 실측)

GitHub 월간 트렌딩과 `created>2026-04` 스타순 검색을 직접 훑은 결과, 하네스 생태계에서 가장 빠르게 자라는 두 축은 **evals**와 **telemetry**였다.

- **`earendil-works/pi`** (97k★) — "Pi Agent Harness". 주목할 것은 `@earendil-works/pi-telemetry`가 **벤더 중립 계약**을 별도 패키지로 분리했다는 점이다: `span`(시작·끝이 있는 작업 1건) · `attribute`(그 작업에 붙는 명명된 사실) · `event` · `status`(ok|error) · 명시적 `context`(전역 current-span 없음). 익스포터·백엔드 의존은 없고, **어댑터 적합성 테스트(conformance tests)** 를 함께 제공한다. 관측을 백엔드가 아니라 **계약**으로 설계한 예다.
- **`raindrop-ai/workshop`** (1.1k★) — "코딩 에이전트가 스스로 eval을 쓰고 돌리게 하라". `ai-evals-course/evals-skills`(441★)도 같은 접근을 스킬로 배포한다.
- **`mattpocock/skills`** (236k★, 월 +50k) — 스킬을 **명명된 실패 모드의 교정 도구**로 프레이밍한다. 가장 흔한 실패는 버그가 아니라 misalignment이고, 처방은 착수 전 질문 공세(`/grill-me`)라는 주장.

> [!tip] 왜 이 축이 중요한가
> 계약 테스트는 **메커니즘**을 검증한다 — 훅이 도는지, 가드가 실패를 내는지. 그게 전부 통과해도 "LLM이 쓴 내용이 맞는가"는 답이 없다. 이 vault도 2026-08-25 시점에 계약 테스트 259개를 갖고 있었지만 산출물 품질 평가는 0개였고, 그래서 `kb-eval` 하네스(골든셋 + LLM-judge + 회귀 게이트)를 추가했다.

## 멀티에이전트 — 합의되지 않은 영역

큐레이션은 반대 입장을 나란히 싣는다. Anthropic의 *Building Effective Agents*는 대부분의 "에이전트"가 실은 워크플로여야 한다고 주장하며 어휘(chaining·routing·orchestrator-workers·evaluator-optimizer)를 정립했다. 반면 Cognition의 *Don't Build Multi-Agents*는 **에이전트 간 컨텍스트 분절이 지배적 실패 모드**라고 반박한다. 결론이 나지 않았다는 사실 자체가 정보다 — 멀티에이전트를 기본값으로 두지 말고, 컨텍스트 분절 비용을 지불할 이유가 있을 때만 쓴다.

## 이 vault의 하네스 자기진단 (2026-08-25)

6가지 책임에 우리 프레임워크를 대조하면:

| 책임 | 이 vault의 구현 | 상태 |
|---|---|---|
| session state | `hot.md` L1 + `session-context` 훅 주입, 기계적 25항목 롤링 | 있음 |
| context budgeting | INJECT 마커(캐시 친화 고정 블록) + L1→L2→L3 계층 | 있음 |
| tool dispatch | cron allowlist를 정확한 스크립트로 고정(`Bash(python3 .claude/foo.py:*)`) | 있음 |
| provider abstraction | 없음 — Claude Code 단일 런타임 전제 | 의도적 비목표 |
| permissions | collect↔review 분리(무인은 큐만, 생성은 동의 후) + `stray-guard.sh` | 있음 |
| recovery | 영수증 계약(rc=1 → 스탬프 미갱신 → 다음 슬롯 재시도) + 데드맨 배너 | 있음 |

관측성은 `span.py`(span/attrs/status 원장)로, 평가는 `kb-eval.py`(골든셋·회귀 게이트)로 2026-08-25에 채웠다. 둘 다 위 실측에서 본 패턴을 우리 규모로 축약한 것이다 — 익스포터·백엔드 없이 JSONL 한 파일, 트리 추적 없이 단일 레벨.
